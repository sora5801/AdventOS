# Session 51 — SSH-2 (RFC 4253) wire protocol

**Goal:** replace session 50's TLS-shuttle "SSH-flavoured" server with the actual SSH-2 protocol — `SSH-2.0-` banner exchange, KEXINIT algorithm negotiation, ECDH key exchange, host-key signature, binary packet protocol with AEAD record layer, plus enough of RFC 4252 (userauth) and RFC 4254 (channels) to run remote commands. Endgoal: a real OpenSSH client talks to `sshd.elf` and gets back a command's output.

End state — manual interop with the host's OpenSSH 10.3:

```
$ SSH_ASKPASS=/tmp/askpass.sh SSH_ASKPASS_REQUIRE=force DISPLAY=:0 \
    ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
        -o KexAlgorithms=curve25519-sha256 \
        -o HostKeyAlgorithms=ssh-ed25519 \
        -o Ciphers=aes128-gcm@openssh.com \
        -o PreferredAuthentications=password \
        -p 2255 guest@127.0.0.1 'id'
Warning: Permanently added '[127.0.0.1]:2255' (ED25519) to the list of known hosts.
uid=1000 gid=1000 pid=16 pgid=16
```

Plus the in-OS loopback `[t33]` selftest (`ssh.elf 127.0.0.1 guest guest id.elf`), all six assertions PASS:

```
[t33] sshd: RFC 4253 SSH-2 loopback (KEX + ed25519 sig + AES-GCM + exec)
  PASS  client received SSH-2.0-* server banner
  PASS  host-key signature verified (ed25519 over H)
  PASS  transport switched to AES-128-GCM after NEWKEYS
  PASS  password auth succeeded (USERAUTH_SUCCESS)
  PASS  remote `id.elf` printed uid=1000 over CHANNEL_DATA
  PASS  server sent exit-status = 0 in CHANNEL_REQUEST
```

## Algorithm picks

We implement exactly one algorithm per slot, matched against OpenSSH's modern defaults:

| Slot | What we offer |
|------|---------------|
| KEX | `curve25519-sha256` (RFC 8731) |
| host key | `ssh-ed25519` (RFC 8709) |
| encryption (both directions) | `aes128-gcm@openssh.com` (RFC 5647 framing) |
| MAC | (empty — AEAD subsumes it) |
| compression | `none` |
| languages | (empty) |

Every primitive already existed in libcrypto from earlier sessions:
- `x25519()` + `x25519_basepoint` from session 36
- `ed25519_keypair_from_seed` / `_sign` / `_verify` from session 39
- `aes_gcm_encrypt` / `_decrypt` with AAD support from session 36
- `sha256` incremental from session 36
- `rand_bytes` from session 36

So this session is entirely **protocol** code — no new crypto.

## What's in scope

In:

- **`libcrypto/ssh.{h,c}`** — wire-format byte-pushers (u8/u32/string/cstring/bool/mpint plus their pullers), an AES-128-GCM packet seal/open pair that does the AEAD work in place inside the caller's buffer (no big static scratch — important because libcrypto links into every TLS program), and the RFC 4253 §7.2 KDF `K_x = HASH(K || H || letter || session_id)`.
- **`user/sshd.c`** — full rewrite. State machine: banner → KEXINIT exchange → `curve25519-sha256` ECDH (`SSH_MSG_KEX_ECDH_INIT` / `_REPLY` per RFC 5656/8731 with the host-key signature over the exchange hash) → NEWKEYS (encryption goes live) → SERVICE_REQUEST `ssh-userauth` → USERAUTH_REQUEST `password` (verify against `/etc/passwd`) → CHANNEL_OPEN `session` → CHANNEL_REQUEST `exec` (pty-req gets CHANNEL_FAILURE since we have no ptys, env gets accepted but ignored, exec runs `sh.elf -c "<cmd>"` with stdout/stderr piped back as `CHANNEL_DATA` frames) → CHANNEL_REQUEST `exit-status` + EOF + CLOSE.
- **`user/ssh.c`** — full rewrite to match. Same algorithm set, verifies the server's ed25519 signature over the exchange hash (with `ed25519_verify`), drives a single exec request, prints CHANNEL_DATA bytes to stdout, picks up `exit-status` to propagate as its own exit code.
- **`kernel/elf.c`** — user stack 4 pages → 16 pages (16 KiB → 64 KiB). `do_kex_ecdh` plus `ed25519_sign`'s SHA-512 scratch was overflowing into the guard page.
- **`kernel/fs.c`** — FS bitmap 2048 → 4096 sectors. The new `sshd.elf` (245 KiB) + `ssh.elf` (197 KiB) pushed the on-disk layout past the previous limit.
- **`user/sh.c`** — `[t33]` rewritten to drive the new client.

Out:

- **PTY pairs / interactive shell.** `pty-req` returns `CHANNEL_FAILURE`. `ssh user@host` (no command) gets a shell-mode placeholder that prints "shell mode not implemented" and closes. Real shell needs `master/slave` pty pairs and a poll/select shuttle, which AdventOS lacks. Pass an explicit command: `ssh user@host '<cmd>'`.
- **Pubkey auth.** Password auth only. We have ed25519 verify ready to go, but `authorized_keys` plumbing isn't here yet.
- **Rekey.** No `SSH_MSG_KEX_INIT` mid-session — long sessions just keep going with the original keys.
- **Sequence-number authentication.** AEAD's per-packet IV counter is enough.
- **OpenSSH extensions (ext-info, server-sig-algs, etc.).** We ignore them silently. OpenSSH falls back gracefully.

## The exchange hash and signature

The KEX hash `H` (RFC 8731 §4) is the SHA-256 of eight fields catenated:

```
H = SHA-256(
    string(V_C) || string(V_S) ||      ← client + server banners (sans CR-LF)
    string(I_C) || string(I_S) ||      ← raw KEXINIT payloads
    string(K_S) ||                     ← server host-key blob
    string(Q_C) || string(Q_S) ||      ← X25519 pubs
    mpint(K)                           ← shared secret
)
```

`string(x)` is SSH-wire encoding: 4-byte BE length followed by bytes. `mpint(K)` is two's-complement big-endian with a leading 0x00 if the MSB is set (RFC 4251 §5).

The signature: Ed25519 over `H`, then wrapped in the SSH "signature blob" shape — `string("ssh-ed25519") || string(64-byte raw R||S)`. The client receives:

```
SSH_MSG_KEX_ECDH_REPLY:
    byte    31
    string  K_S       (the ssh-ed25519 host-key blob)
    string  Q_S       (32-byte server X25519 pub)
    string  sig_blob  (ssh-ed25519 signature over H)
```

It recomputes `H` from its own copies of those eight fields (its banner, its KEXINIT, etc.) and runs `ed25519_verify(sig, H, host_pk)`. If that passes, the server proved possession of the host private key bound to `K_S`, AND that `K_S` is the same one that participated in the ECDH — no MitM.

`session_id = H` from the first handshake. We never rekey, so it's also the final one. KDF labels A/B/C/D pull 32 bytes each from `HASH(K || H || letter || session_id)` for IVs (12 bytes used) and keys (16 bytes used).

## The padding bug that ate three hours

The clean-room implementation almost worked the first time — handshake completed in the loopback test, all six [t33] assertions PASS — but the OpenSSH client died one packet in:

```
debug3: send packet: type 20
debug1: SSH2_MSG_KEXINIT sent
padding error: need 148 block 8 mod 4
```

The Python sniffer confirmed our wire bytes:

```
00 00 00 98 09 14 8c 9a 8f 5f 76 5c a3 4d 86 2b ...
^^ ^^ ^^ ^^ ^^ ^^ ^^^^^ ────────────────────────
length=0x98=152  pad=9  msg=20 (KEXINIT)  cookie...
```

So our `packet_length` field was 152, divisible by 8, padded body alone (`1 + 142 + 9 = 152`) was divisible by 8 — what could be wrong?

The original (buggy) padding calc:

```c
int pad_n = block - ((1 + payload_len) % block);   // body-only alignment
if (pad_n < min_pad) pad_n += block;
```

This makes `(1 + payload + pad) % 8 == 0`. With `payload=142`, that gives `pad=9`. Body = 152, divisible by 8. ✓ But the **wire frame is** `4 + 1 + payload + pad = 156`, and 156 % 8 = 4. ✗

RFC 4253 §6 is explicit if you look hard enough:

> ... such that the total length of (packet_length || padding_length || payload || random padding) is a multiple of the cipher block size or 8, whichever is larger.

The first field, `packet_length`, is **itself** the 4-byte length field — and it's part of the multiple-of-8 constraint. OpenSSH was correct: it computed `need = packet_length(152) - 4 = 148`, then `148 % 8 = 4 ≠ 0`, fatal.

Our loopback selftest passed because our own client had the same bug, so the two ends agreed on a wrong padding rule. OpenSSH's correctness was what exposed it.

Fix is one character:

```c
int pad_n = block - ((4 + 1 + payload_len) % block);   // total-frame alignment
```

For `payload=142`: `(4+1+142)%8 = 3 → pad_n=5`. Body=148, total=152, 152%8=0. ✓ OpenSSH happy.

**Note**: this only applies pre-NEWKEYS. RFC 5647 §6 reworks the rule for AES-GCM: the 4-byte length is sent in cleartext as AAD, NOT encrypted, so the alignment constraint is on the encrypted body alone — `(1 + payload + padding) % 16 == 0`. Our `libcrypto/ssh.c` ssh_packet_seal already had that right.

The single bit of bug-archaeology that helped most: write a Python sniffer in 15 lines, dump 80 hex bytes, eyeball the length field against my own debug printf. It became obvious then that the bytes were right and the interpretation was wrong.

## The stack overflow that ate the second hour

After fixing padding, openssh got through banner + KEXINIT and OUR loopback selftest also got further but… page-faulted at IP 0x400008f6 with CR2 = 0x400f8e9c:

```
[!] CPU EXCEPTION 14: Page fault (err=0x6) at 1b:400008f6
    fault addr (CR2) = 0x400f8e9c
    cause = page not present, write, user mode
```

CR2 is 16,740 bytes below `USER_STACK_VA - 3*PAGE_SIZE = 0x400FD000`, which is the bottom of the four-page user stack. Stack overflow. The disassembly of the faulting IP showed it was right before `ed25519_sign`, inside `do_kex_ecdh`. Stack frames lined up like this:

```
serve_one()
  ↓ a couple hundred bytes
do_kex_ecdh()           ~1.6 KiB local arrays (k_raw + k_s + sig_raw + sig_blob + reply + sha256 ctx)
  ↓
ed25519_sign()          ~6 KiB (expanded sk on stack + SHA-512 transcript work)
  ↓
sha512_update()         a few hundred bytes
```

The deepest path was ~10 KiB. The 16 KiB user stack was tight before — session 36 had bumped it from 1 page to 4 specifically for TLS handshakes — and our SSH handshake is heavier than TLS because of the larger transcript hashing.

Two tightenings landed:

1. The local arrays in `do_channel_requests`, `do_userauth`, and `run_exec` were promoted to `static` (4 KiB + 1 KiB + 2 KiB respectively). Each forked sshd child has its own copy via COW, so this is safe.
2. `USER_STACK_PAGES` 4 → 16 (64 KiB). Even with the static migration, leaving stack room for a future `ed25519_sign_more_things()` is cheaper than relitigating this every session.

## Channel exec mechanics

A successful session ends with the server running `sh.elf -c "<command>"` exactly the way session-50 did, but the I/O routing changes — output goes back as `SSH_MSG_CHANNEL_DATA` frames instead of raw TLS bytes:

```c
int outp[2];
sys_pipe(outp);
int pid = sys_fork();
if (pid == 0) {
    sys_dup2(outp[1], 1);    /* stdout */
    sys_dup2(outp[1], 2);    /* stderr */
    sys_close(outp[0]);
    sys_close(outp[1]);
    const char *argv[] = { "sh.elf", "-c", cmd, 0 };
    sys_exec("sh.elf", argv);
    sys_exit(127);
}
sys_close(outp[1]);

static char buf[2048];
for (;;) {
    int n = sys_read(outp[0], buf, sizeof(buf));
    if (n <= 0) break;
    /* CHANNEL_DATA: byte 94 || uint32 recipient || string data */
    uint8_t pkt[2128]; uint8_t *p = pkt;
    ssh_put_u8(&p, SSH_MSG_CHANNEL_DATA);
    ssh_put_u32(&p, ch->their_id);
    ssh_put_string(&p, buf, n);
    send_packet(c, pkt, p - pkt);
}
sys_close(outp[0]);
int code; sys_wait(&code);
```

After the child exits, we send three more packets:

```
CHANNEL_REQUEST(exit-status = code)
CHANNEL_EOF
CHANNEL_CLOSE
```

OpenSSH receives those, prints the exit code, sends its own CHANNEL_CLOSE, the TCP connection closes.

We do NOT honour client-side window updates carefully. The advertised initial window is 1 MiB, so a typical command's output sails through. A long-running command that produces 100+ MiB of output would eventually have the client refuse to consume more bytes — but we don't even drain WINDOW_ADJUST messages diligently. Good enough for the demo; documented as a known gap.
